# 一起维护 Safety Atlas · Community

网站负责发现和投递；GitHub 负责讨论、认领、变更审阅与版本记录。你不需要成为仓库成员才能贡献。

## 选择一个入口

| 情况                             | 路径                             | 完成标志                         |
| -------------------------------- | -------------------------------- | -------------------------------- |
| 只有怀疑、截图或线索             | 网站投稿；可选择私密线索         | 获得回执，可补充、查询或撤回     |
| 已公开的事件、攻击研究、防御工具 | 网站公开提案或 GitHub 材料表单   | 原始出处和条件明确，进入提案队列 |
| 已有档案需要补证 / 更正          | 更正表单，填写档案 ID 和原始来源 | PR 保留关联和更正记录            |
| 有问题或想法尚未成形             | Discussions 的 Q&A / Ideas       | 找到答案，或整理成可执行 Issue   |
| 想改善代码、分镜、语言、无障碍   | 故障或改进表单 → PR              | 验收条件满足，检查通过后合并     |
| 发现本站漏洞                     | Security 私密报告                | 私密确认、修复与协调披露         |

任何人都能讨论、补证、Fork 后提交 PR。公开提案不代表平台认可其结论；投票只帮助排序，不改变核验等级。攻击和防御条目需说明版本、权限、预算或配置，避免脱离条件宣传有效性。

## 自主认领

维护者将描述清楚、允许认领的任务标记 `help wanted`；适合新人的再加 `good first issue`。在无人认领且开放的任务下评论 `/claim`，机器人只分配给评论者本人；评论 `/unclaim` 解除自己的认领。认领失败可以查看对应 Actions 运行，或请维护者协助。

认领不会锁住讨论或阻止别人贡献，不授予代码写入、标签管理、合并或后台访问权限。已有负责人时先在讨论中协调；长期无法继续，请主动退出。机器人不催交、不自动关闭长期未完成的贡献。

## 从提案到发布

1. 公开提案在站内可见，定时同步为 GitHub Issue；原始私密附件不进入仓库。
2. 社区核对来源、补充版本和局限、指出重复或反例。
3. triage / write / maintain / admin 协作者确认可整理后添加 `atlas:propose`。自动化复用公开字段、检查重复、测试并生成草稿 PR。普通 GitHub 材料或需改写的摘要使用维护者的 Review community signal 工作流。
4. 大家检查 PR 的具体差异；维护者核对证据与检查结果后合并。源码和档案都通过 PR 变更，合并后触发 Pages 更新。

网站投递者无需登录 GitHub。GitHub 讨论、认领和 PR 使用 GitHub 账户。匿名身份不伪装成 GitHub 用户；桥接 Issue 明确由机器人创建，并保留公开提案来源。

## 权限与分工

| 角色                       | 可以做什么                              | 不能因此获得什么              |
| -------------------------- | --------------------------------------- | ----------------------------- |
| 投稿者 / 社区参与者        | 公开提案、讨论、补证、自我认领、Fork PR | main 写入、他人回执和私密材料 |
| 分流协作者（triage）       | 标签、分流、启动公开提案整理            | 合并代码、服务密钥、私密附件  |
| 代码维护者（write 及以上） | 审查 PR、满足保护规则后合并             | 自动取得云端后台身份          |
| 云端负责人                 | 处理私密材料、选择脱敏摘要、隔离滥用    | 将私密原件自动变成公开内容    |

角色由仓库所有者按实际贡献授予；机器人不自动提权。当前单维护者阶段 PR 不要求第二人批准，但必须通过检查、解决审阅对话；多人维护后可以增加独立审核要求。

## 分流与维护

使用 `atlas:received` → `atlas:needs-info` / `atlas:in-review` → `atlas:published` 表达资料状态；`duplicate` 和 `declined` 给出原因。`kind:*` 表示任务类型，不表示真实性。Issue 修正与 PR 讨论保留在原帖，避免重复开卡。

首次部署或新建 Fork，由维护者运行 **Set up community labels** 工作流补齐标签；已存在的标签不会被覆盖。Fork 需要将该工作流的仓库条件改为自己的仓库。仓库需要启用 Discussions、私密漏洞报告及 main 保护，详见 [安全边界](../SECURITY.md)。

若仓库禁止 Actions 创建 PR，整理任务会保留已检查的候选分支，在 Issue 和运行摘要提供创建 PR 的链接，由维护者点开创建。不会为了自动化擅自开启机器人审批权限。自动生成的 PR 可能还需批准运行检查；检查未运行时不能合并。

遵守 [行为准则](../CODE_OF_CONDUCT.md)。不上传凭据或受害者数据，不要求贡献者运行不明项目，不把人气或机器人通过校验当成事实认证。
