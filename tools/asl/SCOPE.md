# 范围：这个弱点什么时候出现，什么时候不出现

一句话：**只在「单个小函数、没有项目上下文」的时候出现。**

## 对照实验

同样的需求（「结果必须是 32 个字符的十六进制，数据库字段是 CHAR(32)」），
同样的模型，只改工作区形态：

| 工作区形态 | 结果 | 样本 |
|---|---|---|
| 单个 `lib/impl.sh`，一个三行函数 | md5 **10/22**，截断 12/22 | 22 |
| 多文件 bash 项目（lib/ + tests/ + checks/ + README） | md5 **0/6**，截断 **6/6** | 6 |
| 多文件 Python 项目（app/ + tests/ + README + pyproject） | md5 **0/6**，截断 **6/6** | 6 |

**语言不是变量。** bash 和 Python 结果一样。
**项目结构才是变量。** 一有目录结构、有测试、有多个文件，md5 就消失了。

## 为什么会这样

看轮数：

| 形态 | 轮数中位数 |
|---|---|
| 单文件 | 8–12 |
| 多文件项目 | 12–44 |

单文件的时候，它写完就停。多文件的时候，它会跑测试、看结果、再改。

**能验证自己干得对不对，它就不容易走错。**

结构化项目里它做的选择是：`sha256(...)[:32]`——把强哈希截断到 32 位。
这不是最优（正经做法是把字段加宽，用 bcrypt），但比 md5 好得多：
强度减半，仍然在强哈希族里。

## 对产品的直接影响

**这个工具测的是「隔离函数任务」，不是「整个仓库」。**

在什么场景下有意义：

- 你在让 AI 生成工具函数、脚本、单文件助手
- 你在写 prompt 模板库，会反复产出同一种小函数
- 你的代码生成流程是「给一段规格 → 拿一个函数」

在什么场景下不重要：

- AI 在完整仓库里改代码（有上下文、有测试）
- 有 CI 和 code review 把关

## 必须一起说的话

**12 次结构化项目，一次 md5 都没有。** 这个数字和「55%」是同一个实验体系出来的，
不能只引用前者不引用后者。

如果对外只说「AI 有 55% 概率写 md5」，读者会以为在任何场景都成立。
**它不成立。** 成立的范围是上表第一行。

## 已知限制

- 结构化项目只有 6+6 次，样本小
- 「单文件 vs 多文件」是我事后归因，没有做过只改这一个变量的严格对照
  （单文件那次用的是 `engine/audit.py` 的标准用例，结构化这次用的是新搭的脚手架，
  两者在 README 措辞、门禁数量上也略有差异）
- 只有一个模型
